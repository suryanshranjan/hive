  4. Schema change tracking: an empty list of outside apps behaves exactly like leaving it out, and two trackers built either way count as equal.
  5. Schema change tracking: two trackers with the same tables but different outside apps are not equal. Example: one naming 'auth' differs from one naming nothing.
  6. Schema change tracking: the list of outside apps must be given as a set; it is no longer quietly converted. Example: handing over ['contenttypes'] as a list is refused with an error instead of being accepted.
  7. Schema change tracking: a tuple, plain text such as 'auth', a frozen set or a dictionary is refused the same way as a list.
  8. Schema change tracking: an empty value that is not a set, such as an empty dictionary or empty text, is refused too; only leaving it out or giving a real set is accepted.
  9. Schema change tracking: naming an outside app that is not installed makes the tracker fail with an error when its tables are first read. Example: naming 'nonexistent' gives 'No installed app with label nonexistent'.
  10. Schema change tracking: a copy of the tracker keeps the same outside apps, so copies still treat 'auth' as an outside app.
  11. Schema change tracking: the apps that have no migration files of their own are passed in automatically when the tracker is built from the migration history, so their tables are pulled in without anyone naming them.
  12. Schema change tracking: when working out which changes are needed, tables of an app listed as outside are not treated as ones the project manages. Example: no new table is created for 'auth' just because it is outside.
  13. Messy or missing details: if the outside-app list is left blank (nothing given), it is treated as no outside apps, and no error appears.
  14. Messy or missing details: if the outside apps are typed as a list like ['auth'] instead of a set like {'auth'}, the tracker refuses it rather than fixing it for you.
