### The owner's rules for this feature (from his interview)
The owner decided each of these himself. Encode every one that touches your area as a test before you land, follow it exactly, and do not stretch it beyond the situation it describes.

- Whenever biz_days is given two valid dates, it counts the Monday-to-Friday days from the start date up to but not including the end date, so Monday 2 Nov to Monday 9 Nov gives 5.
- Whenever biz_days is given the same start and end date, it returns 0.
- Whenever the biz_days start date is after the end date, it returns NULL (no answer), because backwards dates give no answer and never a negative number, a 0 or an error.
- Whenever biz_days spans only a Saturday and/or Sunday (for example Saturday to Monday), it returns 0, because weekends are never counted.
- Whenever biz_days is used, it treats every Monday-to-Friday day as a working day, except that January 1 and December 25 are not working days when they fall on a weekday. No other holidays are excluded.
- Whenever a biz_days date has extra text after its first 10 characters (a time such as '2026-11-02 10:00' or even junk such as '2026-11-02xyz'), it uses only the first 10 characters as the date and ignores the rest.
- Whenever a biz_days date has spaces before or after it, the spaces are ignored and the date is used normally.
- Whenever either biz_days date is NULL, empty, shorter than 10 characters, a number, or not an ISO year-month-day date (for example '2026/11/02', '20261102', '2026-1-2' or the impossible '2026-02-30'), biz_days returns NULL.
- Whenever check_digit is given a code made only of digits, it returns the single GS1-style check digit: the digits are weighted 3, 1, 3, 1... starting from the rightmost digit, summed, and the digit that brings the sum up to the next multiple of 10 is returned (0 if already a multiple), so '629104150021' gives 3.
- Whenever check_digit is given a code with leading zeros, they are accepted and do not change the result, so '007' and '7' both give 9; a code of '0' gives 0.
- Whenever check_digit is given a whole number rather than text, it treats it as the same digits as text (629104150021 gives 3), and a decimal number that is a whole value such as 12.0 is treated as 12.
- Whenever check_digit is given a number with a fractional part (such as 12.5) or text with a decimal point (such as '1.5'), it returns NULL.
- Whenever check_digit is given NULL, a negative number or text starting with '-' or '+', text containing spaces (even leading or trailing) or separators such as dashes, or non-ASCII digits, it returns NULL. Empty text is the exception: it returns the check digit 0, because no digits are left to sum and 0 is already a multiple of 10. Letters in text are not a reason for NULL: they are ignored, and the check digit is worked out from the remaining digits exactly as for a code made only of digits (weights, summing and rounding as in rule 9), so '12A4' gives the check digit for '124', which is 3, and 'A007' gives the same as '007'. If text has letters but no digits at all (such as 'ABC'), it still returns NULL, as it did before. The other cases in this rule still return NULL even when letters are also present, for example '-12A4', ' 12A4', '12-A4', '1.5A' and text with non-ASCII digits.
- Whenever check_digit is given a very long digit string, it still uses every digit with no length limit.
- Whenever discount_price is given a price in cents and a percentage off, it returns the price multiplied by (100 minus the percentage) divided by 100, as a whole number of cents, so 1000 at 10% gives 900.
- Whenever the discounted price falls exactly halfway between two cents, discount_price rounds it up to the next cent, toward positive infinity, so 999 at 50% gives 500 and 1 at 50% gives 1.
- Whenever the percentage given to discount_price is below 0, it is not clamped to 0 and not treated as no discount: the negative percentage is applied as a markup, so the price is multiplied by (100 minus the percentage) divided by 100, which is more than the price. The result is rounded to a whole cent as in the other rules. A 1000-cent item at -20% therefore comes out at 1200.
- Whenever the percentage given to discount_price is above 100, it is capped at 50 percent instead, so the discount applied is 50 percent. The price is multiplied by 50 divided by 100, and the result is rounded as in the other rules. A 1000-cent item at 150% therefore comes out at 500.
- Whenever the percentage given to discount_price has decimals (such as 12.5 or 33.33), they are used exactly and the result is rounded to the nearest cent, so 1000 at 12.5% gives 875.
- Whenever the price given to discount_price is negative, the same calculation is applied and a negative result is returned, with halves rounded away from zero (-5 at 50% gives -3); a price of 0 gives 0.
- Whenever the price given to discount_price has a fraction of a cent, the discounted result is rounded to the nearest whole cent, halves going up, so 1000.5 at 0% gives 1001.
- Whenever discount_price is given a price or percentage as numeric text (such as '1000', ' 10 ' or '1e1'), it reads it as a number and calculates normally.
- Whenever the price or the percentage given to discount_price is NULL, empty text, non-numeric text, or 'nan'/'inf', it returns NULL.
- Whenever format_money is given an amount in minor units and a currency of USD, GBP, EUR, INR, CAD, AUD or CNY, it divides by 100 and shows two decimals with comma thousands separators after the symbol: $, £, €, ₹, CA$, A$ and CN¥ respectively, so 123456789 USD gives '$1,234,567.89'.
- Whenever format_money is given CHF, it shows 'CHF ' with a space and then the amount with two decimals, such as 'CHF 19.99'.
- Whenever format_money is given JPY, it treats it like any other regular currency: it divides the amount by 100 and shows the code 'JPY', a space, and then the amount with two decimals and comma thousands separators, so 1234567 gives 'JPY 12,345.67'.

- Whenever format_money is given any other currency code (such as XYZ or BHD), it shows the code, a space, and the amount with two decimals, such as 'XYZ 19.99'.

So 1050.5 gives '$10.50', 1051.5 gives '$10.52', 1999.5 gives '$20.00', 2000.5 gives '$20.00', and -1999.5 gives '($20.00)', in parentheses with no minus sign as for any negative amount. - Whenever mask_card is given a number instead of text, it treats it as text of its digits; it returns an empty string for empty text and NULL for NULL.

- Whenever rating_band is given an average score above 4.5, it returns 'A'; above 3.5 up to and including 4.5, 'B'; above 2.5 up to and including 3.5, 'C'; and anything else, 'D'. A score exactly on 4.5, 3.5 or 2.5 gets the lower band.
